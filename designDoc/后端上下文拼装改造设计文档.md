# 后端上下文拼装改造 - 设计文档

> 状态：设计稿（未实施）
> 日期：2026-09-20
> 关联文档：[功能设计文档.md](./功能设计文档.md)、[API接口文档.md](./API接口文档.md)

## 1. 背景与目标

### 1.1 现状

当前项目采用**前端维护上下文**的架构：

- 前端 `useChat` 在内存中维护 `messages`，每次发送时取最近 `contextLength * 2` 条（默认 10 轮 = 20 条，按**条数**截断）作为上下文，连同新消息整体 POST 到 `/api/chat`；
- 服务端 `/api/chat` 为**无状态代理**：校验参数后原样转发智谱 API（深度思考模式下仅在头部注入 system 提示词）；
- 持久化由前端触发：每轮结束后（600ms debounce）调用 `POST /api/conversations` **整体覆盖**保存到 SQLite（sql.js，落盘 `D:\talkingLog\db\chat.db`）。

### 1.2 现状问题

| # | 问题 | 位置 |
|---|------|------|
| 1 | 每轮重传全部窗口；**base64 图片每轮重复上传**，几张图即数 MB × 每轮 | `useChat.ts` `getContextMessages` |
| 2 | 按**条数**裁剪，无 token 感知：长消息（贴代码/带图）可能超模型窗口，短对话浪费窗口 | `useChat.ts` `contextLength * 2` |
| 3 | `role: 'error'` 消息会随上下文发给上游（非合法 OpenAI role，可能触发 400） | `addError` 加入的 error 消息未在 `getContextMessages` 中过滤 |
| 4 | 失败轮次（流式一开始即失败）会留下连续两条 user 消息 | `useChat.ts` `sendMessageStream` 错误路径 |
| 5 | 保存为前端触发 + 全量覆盖（DELETE 全部再 INSERT），对话越长写放大越重；前端崩溃可能丢最后一轮 | `App.tsx` 自动保存、`database.js` `saveConversation` |
| 6 | usage 统计语义混乱：`promptTokens` 被覆盖、`totalTokens` 跨轮累加，且不持久化 | `useChat.ts` stats 逻辑 |
| 7 | API Key 前端持有，每轮随 body 明文往返 | `useChat.ts`、`chat.js` |
| 8 | 标题为首条消息 `slice(0, 30)` 硬截断 | `App.tsx` 自动保存 |

### 1.3 目标

切换为**后端上下文拼装**架构：服务端成为对话状态的唯一权威来源（single source of truth），前端只发增量、退化为纯视图层。在此基础上获得：

1. 请求负载恒定（只传新消息 + conversationId，图片不重传）；
2. token 级上下文预算与裁剪；
3. 服务端统一消息清洗（消除问题 3/4）；
4. 每轮原子落库（消除问题 5）；
5. usage 持久化与成本核算（消除问题 6）；
6. 为摘要压缩、重新生成、自动标题、上下文缓存等高级能力打地基。

## 2. 架构对比

### 2.1 数据流对比

**现状（前端维护）：**

```
前端                                     服务端                     上游
 │ POST /api/chat                         │                        │
 │ { apiKey, model,                       │                        │
 │   messages: [最近20条全部历史] } ──────►│ 校验→注入system→原样转发 ──►│ 智谱API
 │ ◄──────────── SSE 流 ──────────────────│◄───────────────────────│
 │ 每轮后前端全量覆盖保存                     │
 │ POST /api/conversations ──────────────►│ DELETE+INSERT 落盘       │
```

**目标（后端拼装）：**

```
前端                                     服务端                     上游
 │ POST /api/conversations/:id/chat       │                        │
 │ { content, images? }    ──────────────►│ ① 读DB取历史             │
 │                                        │ ② 清洗+token裁剪         │
 │                                        │ ③ 拼装messages ─────────►│ 智谱API
 │ ◄──────────── SSE 流 ──────────────────│◄───────────────────────│
 │                                        │ ④ 流结束→增量落库本轮       │
 │                                        │    user/assistant+usage  │
```

### 2.2 差异总表

| 维度 | 前端维护（现状） | 后端拼装（目标） |
|---|---|---|
| 请求负载 | 全窗口重传，图片每轮重复上传 | 恒定几百字节 |
| 裁剪精度 | 按条数 | token 级预算 |
| 上下文策略 | 只能丢最旧的 | 摘要压缩/混合窗口/RAG 可扩展 |
| 数据可信度 | 前端传什么上游收什么 | 服务端统一清洗 |
| 状态一致性 | 前端 debounce 全量覆盖，可能丢轮 | 服务端每轮原子落库 |
| token 统计 | 前端累加、不持久化 | 服务端按轮持久化 |
| 重新生成/按轮删除 | 难（历史在前端内存） | 天然支持 |
| API Key | 前端每轮明文携带 | 可收归服务端 |
| 服务端复杂度 | 无状态 | 有状态（读DB、并发写、幂等） |

## 3. 总体设计

### 3.1 分层职责（目标态）

```
┌─────────────────────────────────────────────────┐
│ 前端（纯视图层）                                   │
│  - 渲染消息、输入、SSE 解析                          │
│  - 只发 { conversationId, content, images? }      │
│  - 不再持有上下文窗口逻辑、不再全量保存                 │
├─────────────────────────────────────────────────┤
│ 服务端                                            │
│  routes/chat.js      聊天端点：增量入口 → SSE 出口    │
│  services/context.js 【新增】上下文拼装管线             │
│    ├─ loadHistory     从 DB 加载会话历史             │
│    ├─ sanitize        清洗（role 校验/合并/剥离）      │
│    ├─ budget          token 预算裁剪               │
│    ├─ summarize       摘要压缩（P2，预留接口）        │
│    └─ assemble        注入 system + 拼装最终 messages │
│  services/database.js 持久化（改造为增量写入）          │
│  services/llmproxy.js 【抽取】上游转发（自 chat.js 抽出）│
└─────────────────────────────────────────────────┘
```

### 3.2 API 变更

| 接口 | 变更 | 说明 |
|---|---|---|
| `POST /api/conversations` | 保留 | 仅用于「新建空会话 / 改标题」 |
| `POST /api/conversations/:id/chat` | **新增** | 增量聊天入口：`{ content, images?, stream? }`，SSE 返回，流结束后服务端落库本轮 |
| `GET /api/conversations/:id` | 保留 | 加载消息 |
| `DELETE /api/conversations/:id` | 保留 | 删会话 |
| `POST /api/chat` | **废弃**（过渡期保留） | 旧的无状态代理，迁移完成后移除 |
| `DELETE /api/conversations/:id/messages/:mid` | **新增（P2）** | 按轮删除（重新生成用） |

### 3.3 数据库 Schema 变更

```sql
-- messages 表：新增 usage 列
ALTER TABLE messages ADD COLUMN prompt_tokens INTEGER;
ALTER TABLE messages ADD COLUMN completion_tokens INTEGER;

-- conversations 表：新增摘要与统计列
ALTER TABLE conversations ADD COLUMN summary TEXT;          -- 溢出历史的压缩摘要（P2）
ALTER TABLE conversations ADD COLUMN total_tokens INTEGER;  -- 会话累计 token
```

`saveConversation`（全量覆盖）保留但仅服务于「新建/改名」；新增：

```js
appendMessage(conversationId, message)  // 增量追加单条消息 + 更新 updated_at
appendUsage(conversationId, messageId, usage)  // 回填该条消息的 usage
```

## 4. 核心模块设计

### 4.1 上下文拼装管线 `services/context.js`

```
loadHistory → sanitize → budget(+summary) → assemble → 最终 messages
```

**sanitize（清洗）**——消除现状问题 3/4：

- 过滤 `role` 不属于 `user/assistant/system` 的消息（error 等）；
- 合并相邻同角色消息（换行符拼接 content）；
- 剥离空 content 且无图片的消息。

**budget（token 预算裁剪）**：

- 估算规则：`token ≈ ceil(中英混合字符数 / 1.6)`，图片按固定预算计（如每张 1024）；
- 预算模型：`模型窗口 − maxTokens 输出预算 − 安全余量(1024)`，默认按 128K 窗口、输出 32768 → 历史预算约 94K，可配置 `contextTokenBudget` 覆盖；
- 策略：从最新往旧累加，超预算即止（滑动窗口）；窗口头部的 `summary`（若有）始终保留。

**assemble（拼装）**：

- 头部插入 system：深度思考模式注入 `DEEP_THINKING_PROMPT`（沿用现有逻辑）；
- 保证首条为 system、随后 user/assistant 交替（异常交替由 sanitize 兜底）；
- 返回 `{ messages, droppedCount, estimatedTokens }` 供日志与调试。

### 4.2 聊天端点 `POST /api/conversations/:id/chat`

```
入参: { content: string, images?: string[], stream?: boolean }
流程:
  1. 校验 content 非空（content 与 images 至少一项）
  2. 服务端取 API Key（见 4.4）
  3. context.assemble(conversationId) 得到历史 messages
  4. 先落库 user 消息（appendMessage，状态 pending）
  5. 转发上游，SSE 流式转发 content/reasoning/usage（沿用现有 streamUpstream）
  6. 流结束:
     - 正常/中断但有内容 → 落库 assistant 消息 + usage
     - 空内容失败       → 落库 error 状态标记（或仅记录日志，不入上下文）
  7. 输出 [DONE]
并发/幂等:
  - 同一会话进行中再次请求 → 409（前端 status!=='idle' 已挡，双保险）
  - 落库写冲突 → sql.js 为单线程内存库，天然串行，无需加锁
```

### 4.3 持久化改造 `services/database.js`

- `appendMessage`：单条 INSERT + `UPDATE conversations SET updated_at=?`，替代每轮全量覆盖；
- 图片仍存 data URL JSON（现状），落盘时机不变（每次写操作后 `persist()`）；
- 兼容：旧数据无需迁移，新列通过 `ALTER TABLE ... ADD COLUMN` 幂等迁移（沿用现有 images 列的 try-catch 模式）。

### 4.4 API Key 收归服务端

- 首选：服务端 `.env` / `config` 注入，前端不再持有 key；
- 过渡：保留前端传 key 的兼容参数，服务端 key 优先；
- `POST /api/chat` 旧端点废弃后，key 不再经前端往返。

### 4.5 前端改造 `useChat.ts`

- 删除：`getContextMessages`、`buildApiContent`（图片拼装移至服务端）、全量 `saveConversation` 自动保存链路；
- `sendMessageStream` 入参改为 `(content, images?)`，body 只含 `{ content, images }`，URL 带 conversationId；
- 新增会话创建流程：发送前若 `conversationId === null`，先调 `POST /api/conversations` 建空会话再发消息（服务端也可在 chat 端点自动建会话，二选一，见 §7 待定项）；
- `stats` 改为渲染服务端回传的按轮 usage。

## 5. 安全与边界

| 风险 | 对策 |
|---|---|
| 图片 data URL 过大撑爆内存 DB | 单图上限（如 5MB）校验；超出拒绝或压缩 |
| 恶意超大 content | content 长度上限（如 64K 字符）校验 |
| SSE 客户端断开 | 沿用现有 `req.on('close')` 销毁上游请求；服务端仍需落库已生成的部分内容 |
| 上游 4xx（如历史超窗） | budget 裁剪兜底；仍失败则返回明确错误，不静默重试 |
| 旧端点兼容 | 过渡期 `/api/chat` 保留并同样接入 sanitize 清洗，双端点并行一个版本后移除 |

## 6. 实施计划

| 阶段 | 内容 | 交付物 | 预估 |
|---|---|---|---|
| P0-1 | sanitize 清洗管线接入现有 `/api/chat`（不动架构，先消除 400 风险） | `services/context.js`（sanitize 部分） | 0.5 天 |
| P1-1 | `appendMessage` 增量落库 + usage 列迁移 | `database.js` 改造 | 0.5 天 |
| P1-2 | 新聊天端点 + context.assemble（loadHistory/sanitize/budget）+ 前端切换 | `POST /api/conversations/:id/chat` | 2 天 |
| P1-3 | API Key 收归服务端 | `.env` + 端点改造 | 0.5 天 |
| P2-1 | usage 持久化与前端统计修正 | 列回填 + UI | 0.5 天 |
| P2-2 | 摘要压缩（溢出历史 → 小模型摘要 → `conversations.summary`） | budget 摘要策略 | 1-2 天 |
| P2-3 | 重新生成 / 按轮删除、自动标题 | 新端点 | 1-2 天 |

里程碑验收标准：

- P0-1 后：含 error 消息的会话再发送不再触发上游 400；
- P1-2 后：抓包确认聊天请求体不随历史增长、图片不重传；杀掉前端页面再重开，会话消息不丢；
- P2-2 后：超过预算的长会话可继续对话且能感知早期内容（经摘要）。

## 7. 待定项（TBD）

1. **会话创建归属**：前端先建空会话 vs 聊天端点自动建会话（倾向后者：少一次往返，id 由服务端生成）；
2. **token 估算精度**：字符估算法（快、不准）vs 接入 `tiktoken`/智谱分词（准、有依赖），P1 先用估算，预留接口；
3. **图片历史策略**：窗口内保留最近 N 张图的完整 `image_url`，更早的降级 `[图片]` 占位——N 的默认值待定（建议 2）；
4. **中断语义**：用户主动中断时，半截 assistant 消息落库并标注 `interrupted` 标记，还是不落库？倾向落库（与现状前端行为一致）。
